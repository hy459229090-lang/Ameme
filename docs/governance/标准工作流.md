# Ameme 标准工作流

> 文档状态：review_ready  
> 适合读者：产品、研发、设计、安全、测试、运营、AI  
> 人类快速阅读：看“主流程”和“每步产物”  
> AI 阅读提示：执行时先确认当前 Job 和 Gate，只推进获批范围。

## 1. 主流程

```text
输入/想法
  -> Intake 收口
  -> Job 与计划
  -> Research / Spike
  -> Gate 决策
  -> PRD + Design + Architecture + Privacy
  -> Engineering Spec
  -> Implement
  -> Validate / Review
  -> Beta
  -> Release
  -> Monitor / Incident / Retro
```

## 2. 每步产物

| 阶段 | 核心动作 | 正式产物 | 结束条件 |
|---|---|---|---|
| Intake | 明确问题、用户、范围、约束和未知项 | Job 草案、WAL 决策 | 目标可执行 |
| Plan | 拆步骤、证据、风险和确认点 | Job `plan_ready` | 用户批准范围 |
| Research | 查官方资料、访谈、实测、保存失败 | `docs/research/`、`research/` | 证据足以做 Gate 决策 |
| Decide | 比较方案和否决条件 | `docs/decisions/` | pass/hold/reject 明确 |
| Product | 定义体验、规则、指标和范围外 | `docs/product/` | PRD 可验收 |
| Design | 用户旅程、信息架构、错误和权限态 | 产品/设计正本 | 关键状态完整 |
| Architecture | 定义数据、接口、同步、模型和安全 | `docs/architecture/`、`docs/privacy-security/` | 技术风险可控 |
| Engineering | 拆 RFC、Schema、迁移和里程碑 | `docs/engineering/` | 可独立开发测试 |
| Implement | 小批量实现、测试、可观测性同步 | `apps/services/packages/connectors` | 自动检查通过 |
| Validate | 功能、数据、性能、安全和体验验证 | `docs/quality/` | 证据满足当前 Gate |
| Release | 灰度、监控、支持和回滚 | `docs/release/` | 明确批准具体版本 |
| Operate | 看指标、处理事故、收集反馈 | `docs/operations/` | 复盘和下一决策完成 |

## 3. 任务执行节奏

1. 读取当前 Job、正本和相关代码。
2. 在 Job 中写清本轮目标、预计改动、验证和阻塞。
3. 实现最小可审查变更。
4. 运行与风险相称的验证。
5. 保存真实结果，明确错误、警告和未覆盖项。
6. 更新正本、索引、状态和 Job。
7. 到达确认门时提交结论、选择和证据，不用过程流水淹没用户。

## 4. 需求变化

- 未改变目标和 Gate 的小调整：直接更新 Job 和正本。
- 改变用户、核心场景、数据范围、隐私边界或发布计划：先写决策记录并重新确认。
- 新发现的严重风险：立即把 Job 标为 blocked，并写清继续所需证据或权限。
- 被否决的方案：保留验证报告和原因，禁止静默删除后重新包装。

## 5. 文档和代码同步

产品规则变化时检查：PRD、体验、Schema、接口、测试、指标和客服说明。  
Schema 变化时检查：迁移、回滚、兼容、同步、删除和测试夹具。  
权限变化时检查：授权界面、隐私说明、日志、云处理和 Agent ContextPack。  
发布变化时检查：版本、构建、监控、回滚和用户通知。

## 6. Review 顺序

`实现/生成 -> 来源与范围审计 -> 自动校验 -> 输入预检 -> 回归测试 -> 人工体验 Review -> 索引/状态同步 -> Gate Review`

Review 结果分为：

- 必须修复：影响正确性、隐私、安全、数据完整性、核心体验或发布。
- 建议修复：不阻断当前 Gate，但需要负责人和期限。
- 已知限制：用户和后续执行者可以明确看到。
