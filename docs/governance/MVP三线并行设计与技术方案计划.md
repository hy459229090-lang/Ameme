# Ameme MVP 三线并行设计与技术方案计划 v0.5

> 文档状态：C1 为 `pass_with_validation_items`；低保真语义与双端原生 UI 优先已确认，进入平台映射与流畅性验证设计\
> 更新日期：2026-07-13\
> 当前阶段：Discovery / MVP 候选设计\
> 目标：同步完成产品设计、交互设计和研发架构技术方案，并用统一追踪矩阵保证三线闭环。\
> 边界：并行设计不代表 Gate 1/2 已通过，也不授权直接开始生产开发或发布。

## 1. 为什么必须三线并行

Ameme 的页面、数据获取和底层架构高度耦合：

- 产品规则决定需要覆盖哪些事件、数据和权限。
- 交互设计决定用户如何授权、补充、纠错、找回和删除。
- 研发架构决定这些动作能否在双移动端、Agent、本地存储和选择性云同步中真实成立。

因此不采用“PRD 写完 -> 交互交付 -> 研发评估”的串行方式。三线从同一组已确认决策出发，按共同里程碑并行推进。

## 2. 三条工作线

### A. 产品设计线

目标：明确 MVP 为什么存在、服务谁、解决什么、包含什么、如何判断有价值。

正式产物：

- `docs/product/MVP产品设计规格.md`
- `docs/product/MVP范围与体验设计原则.md`
- 来源与授权包产品规则
- 产品指标、验收标准和范围外清单

完成条件：

1. 首批用户、核心场景和价值承诺明确。
2. Mobile 双端、Agent 集成和 Event Core 的 MVP 范围可验收。
3. 每项能力有用户价值、使用路径、数据边界、失败处理和指标定义。
4. 产品范围不会要求尚未验证或无授权的数据能力。

### B. 交互设计线

目标：把产品规则变成用户可完成的路径、页面、状态和反馈。

正式产物：

- `docs/product/Mobile信息架构与数据获取联动.md`
- `docs/product/Mobile交互设计规格.md`
- `今天`、搜索页、平台原生设置入口和事件详情低保真结构
- iOS/Android 原生组件映射与流畅性测量计划
- 首次授权、上传补充、搜索、纠错、删除和异常状态
- 双端系统组件之上的有限品牌强调 Token 与媒体表达

完成条件：

1. 主路径、分支、返回、取消和失败状态完整。
2. 每个页面模块映射到正式对象、来源、权限和获取状态。
3. iOS/Android 平台差异不改变核心语义。
4. 关键流程完成低保真和可交互原型验证。
5. 可访问性、隐私解释和错误恢复进入设计，而不是开发后补。

### C. 研发架构技术方案线

目标：证明产品与交互可以由可实现、可测试、可演进的系统支撑。

正式产物：

- `docs/architecture/MVP研发架构技术方案.md`
- 后续工程 RFC、Schema、API、同步和安全决策
- Mobile 获取适配器、Agent MCP/Skill/API、Personal Event Core 组件边界
- Prototype 与 MVP 工程版本切片

完成条件：

1. 系统上下文、组件、领域对象、接口和数据流明确。
2. 本地优先、选择性同步、离线、冲突、删除传播和审计可实现。
3. 照片、语音、位置、日历、健康和 Agent 获取有适配与降级路径。
4. `RecallQuery`、日历索引、关键词搜索和未来 Agent 搜索使用同一权限模型。
5. 模型调用、成本、性能、可观测性、安全与隐私风险有方案和验证点。
6. 技术栈只在证据足够后形成决策记录，不以文档偏好代替 Spike。

## 3. 统一追踪矩阵

三线以稳定能力 ID 协作。每项进入 MVP 的能力必须在同一行闭环：

| 字段 | 说明 |
|---|---|
| Capability ID | 稳定标识，例如 `TODAY-001`、`CAPTURE-VOICE-001` |
| 用户价值 | 用户为什么需要 |
| 产品规则 | 自动、询问、禁止或条件使用的边界 |
| 页面与交互 | 入口、主路径、异常和恢复 |
| 来源与权限 | 数据来自哪里，授权到什么范围 |
| 领域对象 | SourceObject、Observation、Event、DayLedger 等 |
| 组件/API | 哪个端、服务、接口或 Connector 承担 |
| 存储与同步 | 原始、结构化、索引和派生数据去哪里 |
| 指标 | 如何判断价值、准确、负担和信任 |
| 验证证据 | 需要的测试、Spike、原型或用户证据 |
| 状态 | 候选、已确认、待验证、阻塞或否决 |

关闭规则：产品、交互、架构、隐私或验证任一列为空，能力不能进入 MVP Ready。

## 4. 并行阶段与共同检查点

### P0：共同基线（已完成）

- 首批用户为 AI 使用者，Mobile 基础体验也可独立服务日常用户。
- iOS + Android Native Mobile、Agent MCP/Skill/API 与 Personal Event Core 进入 MVP 候选。
- 主输出为 `今天`；右上放大镜按钮进入历史搜索页，搜索页采用统一历史日流，上滑加载、日历跳转、关键词筛选；设置按平台使用原生二级入口。
- 照片、语音、机会式位置、日历和健康授权包为 Mobile 核心来源。
- MVP 先采用效率风格，情绪风格后置。
- iOS 与 Android 统一产品语义和数据契约，但 UI 分别使用 SwiftUI 系统组件与 Jetpack Compose Material 3/系统能力，不追求像素一致。

### P1：三线规格 v0.4（C1 已完成）

产品线输出范围、规则、指标和验收；交互线输出页面、路径和状态；架构线输出系统、数据、同步、安全和工程切片。

共同检查点 C1：

- 三份规格使用相同术语和范围。
- 不存在只有页面没有数据、只有数据没有用途、只有架构没有产品入口的能力。
- 所有未确定事项明确标记为待确认或待验证。

### P2：详细设计与定向验证

- 产品：PRD 验收条目和指标事件。
- 交互：低保真、关键状态、权限旅程和可交互原型。
- 架构：候选技术栈、Schema/API、同步/删除、模型路由和定向 Spike。

共同检查点 C2：逐条评审统一追踪矩阵，形成 Prototype 边界。

### P3：Prototype 闭环

用合成的一天和获准的真实来源验证；不设面向用户的最小来源组合，夹具必须包含单来源和数据稀疏日：

`获取 -> 形成事件 -> 今天查看 -> 补充/纠错 -> 历史日流/日历跳转/关键词筛选 -> 删除传播`

共同检查点 C3：产品价值、交互可用性和技术可行性都具备真实证据，才建议 Gate 2 结论。

### P4：MVP Ready

补齐 PRD、设计正本、架构/RFC、隐私威胁模型、指标埋点、成本、测试、里程碑和发布计划，进入 Gate 3 评审。

## 5. 三线协作规则

1. 三线可以并行写候选，但共同术语以当前正本和 Event Schema 为准。
2. 产品范围变化必须同步检查交互、Schema、权限、指标和测试。
3. 交互新增状态必须说明触发它的数据状态和恢复动作。
4. 架构发现平台限制时，先回写约束和可选降级，不静默改变体验。
5. 无证据的技术选择标为候选；无验证的用户判断标为假设。
6. 每个共同检查点只提交少量实质性取舍给产品负责人确认。
7. 三线文档完成不等于 Gate 通过，仍需用户研究、平台 Spike 和 Prototype 证据。

4. 建立双端真机的启动、滚动、输入、搜索、保存确认、恢复、稳定性和资源指标基线；数值门槛在基准后确定。
