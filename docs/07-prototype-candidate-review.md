# Ameme Prototype 候选评审 v0.2

> 文档状态：`plan_ready`，产品主链已重构，等待通用来源样本与正式 R0 用户证据\
> 当前 Gate：Gate 1 `hold`\
> 核心调整：Prototype 不再被定义为一个“工作记忆工具”，而是同一个 DayLedger Core 加不同来源组合。

`DayLedger` 是内部名称，用户看到的是“我的一天/每日事件记录”。

## 1. 当前结论

首个核心 Prototype 应验证：

> 系统能否从普通人也可使用的若干来源，尽可能还原一天中有意义的事件，把事件清晰描述并可追溯地保存；之后才生成总结和长期记忆。

因此将原来的三个“产品候选”重构为：

- 一个共同核心：`DayLedger Core`。
- 三个来源包：通用/移动、专业桌面、沟通与服务。
- 多种输出：时间线、日总结、找回、ContextPack。输出不决定底层数据模型。

早期产品形态采用双主采集入口：

- Agent 入口：通过 MCP/Skill/API 寄生于现有 Agent 产品，完成工作上下文获取、历史查询和结果写回。
- Mobile 入口：通过 Native App 获取手机与现实生活中独特的获准来源，并完成记录、查看“我的一天”、后补描述、纠错和数据管理。

Web App、小程序和 Browser Extension 作为低门槛触达、跨端查看和特定来源补充；独立 Native Desktop Agent 暂不作为首版前提。

端优先级遵循：在权限、安全和用户控制的硬门槛内，先比较对一天事件覆盖的独特增益，再比较可覆盖用户规模，最后比较开发与运行成本。

FORMALdoc 只用于验证“专业桌面来源包”，不能代表普通用户，也不能决定产品的信息架构。

## 2. Core Prototype：DayLedger

### 要证明什么

1. 不同格式的输入都先形成 `SourceObject` 和 `EventCandidate`。
2. 多个碎片可以合并为时间有序的 `Event/Episode`。
3. `DayLedger` 能清楚描述一天发生了什么，并显示来源、置信度和缺口。
4. 用户可以补一件漏掉的事、修改错误事件或删除不想保留的事件。
5. Summary/Memory 从 DayLedger 生成，删除或修订事件后可以重算。

### 最小输入

Prototype 不先依赖完整系统权限，使用三种低风险输入即可：

- 一份用户主动选择的照片、截图、文件或网页。
- 一份日历/时间信息或合成的系统事件。
- 一句文字/语音补充。

可再加入一个增强来源包做对照，但核心 Schema 和页面不随来源改变。

### 最小输出

```text
来源对象
 -> 事件草稿
 -> 按时间合并成“我的一天”
 -> 补漏/纠错
 -> 保存 DayLedger
 -> 生成一段日总结
 -> 修改底层事件后验证总结可重算
```

## 3. 来源包 A：Native Mobile 现实生活来源

### 目标用户

不使用 Coding Agent、Git 或项目工作区的普通用户，包括生活记录者、学生、游戏玩家、家庭用户和一般职场用户。

### 来源层级

- 无权限也能用：文字、语音、相机、一键分享、文件/照片选择。
- 分项授权增强：日历、照片建议、地点/活动建议、健康/运动摘要和平台允许的设备信息。
- Connector 增强：邮件、账单导入、游戏、出行、音乐等官方能力。

### 要验证的问题

- 只用通用入口，能覆盖一天中的哪些事件？
- 用户愿意在发生时一键记录，还是晚间补空白时间段？
- 照片/日历能否还原事件，而不只列出媒体和日程？
- 普通用户是否能理解 DayLedger、来源和删除，而不需要理解“Memory Schema”。

当前缺口：iOS/Android 真机证据仍不足，但 Mobile 的独特数据价值已进入主产品形态，不再作为远期附属端。

## 4. 来源包 B：Agent 工作流增强来源

### 目标用户

知识工作者、创作者、研发、产品经理和研究者。

### 来源

- 宿主 Agent 当前任务、获准工作区和显式选择的文件/产物。
- MCP/Skill 工具调用、用户要求记录的决定、结果和后补描述。
- Browser `activeTab` 一键记录。
- 可选 Git、日历、会议、IM Connector；不要求 Ameme 自建完整桌面采集器。

### 当前证据

- Windows 文件事件低风险 Spike 已通过。
- Chrome `activeTab` 合成页低权限闭环已通过。
- FORMALdoc 只读样本说明 Git、状态看板、Job 和文件元数据之间存在明显新鲜度与权威差异。

### 定位

这是提高工作日事件覆盖的增强包，也是早期 AI Native 用户的重要入口；Ameme 寄生于现有 Agent 产品，而不是先复制一套桌面 Agent。其结果必须进入与 C 端产品相同的 Event/每日事件记录模型。

## 5. 来源包 C：沟通与服务增强来源

### 目标用户

会议密集的管理者、销售、顾问，以及希望记录游戏、运动、消费和出行的人。

### 来源

- 用户转发、@Bot、授权会议转录或日历。
- 邮件、组织认可的 IM App/API。
- 游戏/运动/出行/消费的官方 API 或用户导入。

### 边界

- 不以全量 IM 历史、隐藏录音或非官方抓取登录态作为 Prototype 前提。
- 他人声音、聊天和关系信息必须有更严格的权限、告知和空间隔离。

## 6. 清晰描述标准

每个 Event 同时保存结构化事实和用户可读描述：

| 层 | 内容 | 示例要求 |
|---|---|---|
| 事实字段 | 时间、主体、动作、对象、地点、结果、来源、置信度 | 缺失字段允许为空，不编造 |
| 用户描述 | 一句自然语言说明发生了什么 | 区分事实与推断，避免应用流水账 |
| 来源解释 | 来自照片、日历、文件、分享还是用户补充 | 可打开或撤回 |
| 事件关系 | 属于哪个 Episode、人物、项目或生活场景 | 允许多标签和修订 |

日总结只引用这些 Event/Episode，不把摘要正文当作唯一存储。

## 7. 核心指标

- 已复盘时段的事件确认覆盖率与用户补充遗漏数。
- Event 时间错序率、错误合并率和描述修正率。
- 从一个事件回到来源的成功率。
- 补漏/纠错耗时。
- Summary 对 DayLedger 的事实一致性。
- 删除一个来源后 Event、Summary、Memory 和索引的重算结果。
- 每种来源组合的覆盖增益、权限成本和资源成本。

小样本只报告原始计数和具体遗漏，不用比例包装市场结论。

## 8. 否决条件

- Prototype 只能在拥有 Git/工作区的用户身上成立。
- 系统只能生成漂亮摘要，却没有可核验的 Event/DayLedger。
- 必须默认开启全屏、全音频或全量聊天才能还原一天。
- 用户无法发现时间线缺口、修改事件或回到来源。
- 删除原始来源后，摘要和长期记忆仍保留不可解释的结论。

4. Gate 1 在真实用户和来源验证完成前保持 `hold`。
