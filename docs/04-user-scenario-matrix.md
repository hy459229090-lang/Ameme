# Ameme 用户与场景矩阵 v0.2

更新日期：2026-07-13\
状态：竞品/平台桌面证据已补充，等待用户访谈与行为实验验证

## 1. 当前判断

Ameme 的目标用户不应只按职业划分，还要按“主要记忆发生在哪个端、需要在哪个场景使用”划分。同一个人也可能同时属于多个空间，例如工作空间、个人空间、家庭空间和健康空间。

所有用户共享同一个基础任务：尽可能覆盖一天中有意义的事件，形成清晰、可追溯的每日事件账本。职业和设备只决定“从哪些来源获得信号”以及“最后如何使用”，不改变 Event/DayLedger 核心模型。

## 2. 用户-端-任务矩阵

| 用户群 | 主要端 | 高频信息源 | 最想解决的任务 | 可能的第一价值 | 主要信任边界 |
|---|---|---|---|---|---|
| AI Native 知识工作者 | Desktop、Browser、Agent | 网页、文档、代码、文件、AI 对话、会议 | 还原项目进展、找回决策、给 Agent 补上下文 | 工作记忆、项目回顾、ContextPack | 公司数据、密钥、私聊、客户资料不能混入个人云 |
| 管理者/销售/顾问 | Communication、Calendar、Mobile | 会议、邮件、IM、联系人、日历 | 记住承诺、客户背景、跟进事项 | 人物/客户记忆和行动提醒 | 他人同意、组织管理员授权、商业秘密 |
| 学生/长期学习者 | Browser、Desktop、Mobile | 网课、网页、PDF、笔记、截图、语音 | 记录学过什么、形成知识轨迹、安排复习 | 学习时间线和知识回顾 | 课程版权、学校账户数据、错误知识归纳 |
| 生活记录者 | Mobile、Share Sheet | 照片、视频、地点建议、日历、语音 | 不写长日记也能保留重要一天 | 每日生活卡片和家庭回忆 | 家人照片、未成年人、精确位置 |
| 自我量化用户 | Mobile、Wearable、Import | 运动、睡眠、健康、消费、出行 | 看懂习惯、状态与行为变化 | 周/月趋势和目标复盘 | 健康与财务必须独立空间，禁止未经同意跨用途分析 |
| 游戏玩家 | Desktop/Mobile、Game Connector | 游戏时长、战绩、成就、截图、社交 | 保存游戏经历、进步轨迹和高光时刻 | 自动游戏日志和赛季回顾 | 游戏账号凭证、反作弊、队友信息 |
| 创作者/自由职业者 | Desktop、Mobile、Browser | 素材、文件、网页、客户沟通、发布平台 | 追踪灵感到成品、复用素材和项目经验 | 创作项目记忆和素材溯源 | 客户版权、未发布内容、商业使用范围 |

## 3. 跨端体验不是同一界面的复制

### Agent 集成入口更适合

- 寄生于用户已经使用的 Coding Agent/AI 工作流。
- 围绕当前任务读取最小历史上下文，记录决定、产物和结果。
- 通过 MCP/Skill 提供自然语言交互，通过 API 提供稳定领域能力。
- 用户不需要另开一个 Ameme Desktop 才能管理工作记忆。

### Native Mobile App 更适合

- 获得 PC 和 Agent 难以覆盖的现实生活与手机系统来源。
- 文字、语音、相机、照片/文件和分享记录。
- 在分项授权下使用日历、位置、健康、活动建议等平台能力。
- 查看“我的一天”、后补描述、纠错、删除和管理授权。

### Web App/小程序更适合

- 降低访问门槛、扩大用户覆盖。
- 跨端查看、搜索、补充、总结和账户/权限管理。
- 在不能安装 App 或只需轻量记录时提供入口。
- 不承担只有 Native App 才能稳定获得的系统信息。

### Communication Connector 更适合

- 围绕群、项目、会议和人物获取明确的沟通事件。
- 通过组织认可的 Bot/App/Graph 权限接入。
- 生成承诺、决定和跟进，而不是无差别保存全部聊天。

### MCP / Skill / API 更适合

- 针对明确任务请求一小段获准上下文。
- 把 Agent 的成果、决定和用户反馈先写回 EventCandidate，再按治理规则形成记忆。
- 记录调用目的、范围和使用结果。

其中 MCP/Skill 是宿主 Agent 中的用户交互和工具入口，API 是底层服务合同；三者不是一个单独“高级用户页面”。

## 4. 通用视图与隔离空间假设

建议默认空间：

| 空间 | 默认内容 | 默认云策略 | 默认跨空间策略 |
|---|---|---|---|
| Work | 文件、网页、代码、会议、工作 IM | 结构化事件可选同步；原始内容默认本地 | 不向 Personal/Family 自动共享 |
| Personal | 日常网页、个人文件、语音和主动记录 | 已确认记忆可加密同步 | 查询时可临时引用其他空间 |
| Family | 家庭照片、共同事件、纪念日 | 按共享成员和相册选择 | 默认禁止 Agent 外发 |
| Health | 运动、睡眠和健康数据 | 默认设备内；启用健康功能后单独授权 | 不用于工作效率或广告推断 |
| Finance | 账单、消费和财务文件 | 默认设备内；摘要同步需单独开启 | 不与情绪/健康自动关联 |
| Custom | 用户自定义项目或主题 | 用户设置 | 用户设置 |

通用视图不复制数据，而是在查询时按当前身份和权限聚合各空间的结果。

## 5. R0 必须通过访谈验证的问题

1. 用户上一次“明明做过但找不到”的具体经历是什么？
2. 用户当前如何写日报、保存照片、管理会议纪要或记录游戏经历？
3. 哪类信息允许后台获得，哪类只能一键分享，哪类绝不能进入系统？
4. 用户愿意花多少时间确认一天？什么错误会立刻失去信任？
5. 用户愿意为什么付费：少写记录、找回历史、长期洞察、Agent 上下文还是云同步？
6. 工作、个人、家庭、健康和财务是否需要不同账户、不同密钥或只是不同空间？
7. 当用户要求删除一个来源时，期望历史摘要和 AI 记忆如何变化？
8. 除了事实事件，用户最希望系统覆盖哪些记忆类型：决策、承诺、发现、方法、人物、偏好、情绪还是生活高光？哪些必须由用户主动补充？

## 6. 当前优先级是假设，不是结论

桌面 AI Native 用户依然是较易进行技术验证的候选，但不能因为容易开发就直接等同于最佳产品切入口。R0 应把以下三个差异显著的场景并行比较：

- 工作与 Agent 上下文。
- 手机生活事件与每日回顾。
- 沟通、承诺和人物记忆。

比较完成后再决定第一个 Prototype。

## 7. 来源包排序，而不是三种独立产品

| 来源包 | 当前证据 | 主要缺口 | 当前用途 |
|---|---|---|---|
| 通用/移动基础来源 | iOS Journaling Suggestions、iOS/Android Picker/Share 有官方低权限路径；文字、语音、文件/照片选择无需专业工具 | 缺真机、普通用户和通用一天样本 | DayLedger 必须优先补齐的基础来源包 |
| 专业桌面增强来源 | Windows 元数据部分实测；Chrome `activeTab` 低权限闭环实测；FORMALdoc 证明来源冲突与噪声真实存在 | 缺 AI Native 用户访谈和真实 Agent 任务对照 | 技术证据最强的增强来源包，不代表产品默认用户 |
| 沟通与服务增强来源 | 会议、邮件、游戏/健康等有官方或导入路径 | 音频/他人同意、组织权限、跨服务差异大 | 待基础 Event/DayLedger 模型稳定后按场景接入 |

三类来源都必须进入同一个 DayLedger Core。完整桌面证据见 `research/R0用户任务与竞品证据_20260713.md`；真实验证按 `research/R0用户访谈与行为验证计划.md` 执行。Limitless/Rewind 的停用案例说明“全量持续采集”不能因为技术可行就成为默认产品策略。
