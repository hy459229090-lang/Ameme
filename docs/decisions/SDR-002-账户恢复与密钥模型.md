# SDR-002：账户归属与设备密钥模型

- 状态：accepted（产品负责人选择账户优先、无用户密钥 UX）
- 日期：2026-07-14
- 决策人：产品负责人
- 影响 Gate：Gate 3–6
- 替代/被替代：替代原混合 recovery-key 决议；与 SDR-001/ADR-006 联动

## 背景与问题

产品负责人希望“登录账户就是对应账户的数据”，首版不引入恢复密钥、助记词或用户手动管理空间密钥。同时 D1 选择 LAN/P2P、无数据云，因此账户归属与异地数据恢复必须分开表达。

## 已接受决议

1. `owner_account_id` 是所有 space、Event、Raw 索引和设备的归属命名空间；同账户设备可以在 LAN 中同步获准数据。
2. 用户只完成普通登录/重新认证，不接触 recovery key、助记词或手动密钥交换。
3. 本地数据库和 Raw 仍使用系统 Keychain/Keystore 管理的设备包装密钥与透明数据密钥；“用户不管理密钥”不等于明文存储。
4. 新设备登录同账户后，通过强认证和现有在线设备建立加密会话并同步；设备加入、移除和首次全量同步产生通知与审计。
5. 账户/身份服务不保存用户记忆数据。没有任何旧设备在线时，只能建立空的本地库，不能恢复旧内容。

## 产品后果

- Onboarding 必须写清：“账户用于识别和连接你的设备；首版数据没有云端备份。”
- 登录账户被盗仍可能在同一 LAN/设备发现窗口内发起同步，因此需要重新认证、设备通知、速率限制和可撤销设备会话。
- 若未来要求“只登录就能在任何地方恢复”，必须增加云备份或用户托管备份；这是新产品决策，不得由工程暗中实现。

## 待验证项

身份提供方、离线登录缓存、设备加入 UX、账户接管、Keystore/Keychain 轮换、设备全部丢失、同账户恶意设备、客服解释和迁移策略。
