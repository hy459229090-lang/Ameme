# Ameme 记忆反馈与类型覆盖框架 v0.1

> 文档状态：事件覆盖后的辅助机制，等待 R0 真实样本验证\
> 适合读者：产品、设计、算法、研发、研究\
> 核心问题：每日事件账本形成后，系统如何通过低负担反馈补漏、纠错，并逐步形成长期记忆。

## 1. 前置边界

反馈不是产品第一层，也不能代替一天事件覆盖。产品主链先完成：

```text
多端信号 -> EventCandidate -> Event/Episode -> DayLedger -> 清晰存储
                                                 -> Summary/Memory/Recall
```

本框架只负责修复 DayLedger 的遗漏和错误，并帮助系统从可信事件中形成长期记忆。Ameme 不应把“采集到的信息量”当成事件覆盖，用户反馈用于回答：

1. 这件事是否真的发生、时间和描述是否正确。
2. 一天中还有哪些事件没有被来源覆盖。
3. 哪些事件值得形成长期记忆，以及下次类似信号应自动记录、先问还是忽略。

因此产品闭环应是：

```text
DayLedger 事件草稿 -> 补漏/纠错 -> 可信每日事件
        ^                         |
        |---- 个性化覆盖规则 -------|
可信每日事件 -> 可选的长期记忆 -> 总结/找回/使用反馈
```

目标不是让用户逐条给记忆分类，而是先把一天说明白。基础记忆类型用于后续整理和检索；用户通过补漏和自然语言修正，逐渐扩展个人记忆模型。

## 2. 覆盖不是一个数字

需要同时观察四种覆盖：

| 维度 | 要回答的问题 | 例子 |
|---|---|---|
| 每日事件覆盖 | 一天中有意义的事件是否被发现、按时间组织 | 上午工作、午餐、出行、游戏、家庭沟通 |
| 来源覆盖 | 哪些端和信息源能提供证据 | 文件、网页、照片、分享、IM、游戏 |
| 语义类型覆盖 | 系统知道这是哪一种记忆吗 | 决策、承诺、发现、项目状态、生活时刻 |
| 使用覆盖 | 记忆能否在真实任务中发挥作用 | 日报、找回、ContextPack、提醒、复盘 |
| 信任覆盖 | 用户能否理解、纠正、隔离和删除 | 来源展开、空间、保留期、撤回传播 |

R0/MVP 不声称“完整记住一天”。只报告在已复盘样本内的确认覆盖率和遗漏率。

## 3. 基础记忆类型

记忆类型采用多标签，不使用互斥目录。一个片段可以同时是“决策 + 项目状态 + 承诺”。

| 基础类型 | 用户真正想保留的内容 | 主要自动证据 | 常见反馈补充 |
|---|---|---|---|
| 经历片段 | 一段时间里主要做了什么 | 应用、文件、网页、日历、地点 | 真实意图、开始/结束边界 |
| 产物与里程碑 | 创建、修改、发布或交付了什么 | 文件、版本、链接、构建结果 | 哪个是正本、是否真的交付 |
| 项目与目标状态 | 当前进展、阻塞、下一阶段 | Job、任务系统、提交、日历 | 已完成/进行中/阻塞的真实状态 |
| 决策与理由 | 选了什么，为什么放弃其他方案 | 会议纪要、文档修改、主动记录 | 决策理由、适用范围、可逆性 |
| 承诺与下一步 | 谁要在什么时候做什么 | 会议、IM、任务、日历 | 责任人、期限、是否仍有效 |
| 发现与认知变化 | 新发现、验证结果、观点变化 | 调研、实验、报告、搜索轨迹 | “这改变了我什么判断” |
| 方法与程序 | 可复用的做事方法、踩坑和修复 | 脚本、SOP、命令、复盘 | 何时适用、失败条件 |
| 人物与关系上下文 | 与谁围绕什么合作、偏好和历史 | 通讯录、会议、用户主动授权的沟通 | 关系意义、敏感边界、是否可跨空间 |
| 偏好与边界 | 喜欢什么、拒绝什么、怎样协作 | 重复选择、设置、明确表达 | 这是长期偏好还是一次选择 |
| 模式与习惯 | 重复出现的行为或状态 | 多日聚合信号 | 是否有意义、是否只是工作安排 |
| 情绪与身心状态 | 当时感受、精力、压力、恢复 | 主要依赖主动表达和获准健康数据 | 情绪强度、原因、是否允许关联 |
| 生活时刻与成就 | 家庭、旅行、游戏、运动等值得回忆的时刻 | 照片、地点、游戏/运动数据、分享 | 人物、意义、高光原因 |

不同用户使用不同来源组合，不能用 Workday 样本决定所有人的记忆类型。人物、偏好、模式、情绪和生活类型只在用户主动补充或证据充分时进入，不从单一桌面元数据强推断。

## 4. 反馈动作设计

### 4.1 事件草稿级反馈

DayLedger 中的事件草稿首屏只提供三个主动作：

- `对`：事件、时间和描述基本正确。
- `修改`：编辑发生了什么、时间、人物、地点、结果或来源。
- `没有发生/不记录`：误判、重复、太细碎或用户不希望保存。

展开后才提供：重要性、合并/拆分、移动空间、保留期、删除来源引用和“以后类似内容怎么处理”。

### 4.2 覆盖发现反馈

每日查看先围绕时间线缺口，而不是要求用户思考抽象记忆类型：

> 上午 / 下午 / 晚上还有什么事情没有出现？

用户可以用一句话、语音、分享对象或“从最近照片/文件中选择”补充。最后可以再问“今天最重要但漏掉的是什么”，用于发现高价值遗漏。`add_missing` 既新增 EventCandidate，也用于估计当前系统的遗漏分母。

后补描述是正式输入方式，不是低质量数据的兜底。系统保存“何时补充”和“描述的是何时发生的事”，可以关联已有事件或创建新事件；旧版本和来源仍然保留。

### 4.3 使用时反馈

记忆被搜索、日报、提醒或 Agent ContextPack 使用后，再收集任务结果：

- 有帮助。
- 内容正确但不相关。
- 过时。
- 缺少关键上下文。
- 引用了不应访问的空间或来源。

“保存时正确”不等于“使用时有价值”，两种反馈必须分开。

## 5. 各端使用自然入口，而不是复制同一界面

| 端/场景 | 候选从哪里来 | 最低负担反馈 | 覆盖更多类型的入口 |
|---|---|---|---|
| Agent 集成（MCP/Skill/API） | 宿主 Agent 当前任务、获准文件/工作区、工具调用和结果 | 在对话中“记一下/补充/更正”；任务结束写回 | 补决定、项目状态、方法、结果和阻塞 |
| Browser | 用户点击扩展后获得当前页 | 保存/忽略/归项目 | “我从这页学到了什么”补认知变化 |
| Native Mobile App | 文字、语音、相机、照片/文件、分享、日历和分项授权的系统来源 | 查看“我的一天”、补一句、修改、删除、管理授权 | 生活时刻、情绪、人物、地点和遗漏事件 |
| Web App/小程序 | 用户主动输入、上传和已同步事件 | 跨端查看、补充、搜索、总结和管理 | 扩大用户覆盖，不代替原生数据获取 |
| IM/会议 | 转发、@Bot、授权会议转录 | 确认决定/承诺，不读全量历史 | 责任人、截止时间、关系上下文 |
| 未来 Native Desktop | 文件事件、前台应用和端侧处理 | 补充宿主 Agent 无法获得的桌面信号 | 仅在覆盖增益被证明后建设 |

这落实了低权限边界：跨端无感是“各端使用最自然的系统入口并逐渐减少重复确认”，不是所有端后台全量读取。

## 6. 反馈节奏与主动学习

| 时机 | 时长目标 | 只问什么 |
|---|---:|---|
| 捕获当下 | 5 秒内 | 是否保存、属于哪个空间；其余以后补 |
| 每日复盘 | 中位数 2 分钟内 | 高置信候选批量确认、低置信候选纠错、最重要遗漏 |
| 任务使用后 | 1 次点击或一句话 | 是否有用、缺失、过时、越权 |
| 每周回顾 | 仅有新发现时出现 | 新类型、新模式或规则是否成立 |

系统只针对高价值不确定性提问：

1. 可能成为重要记忆但证据冲突。
2. 用户重复修改同一字段或类型。
3. 同类遗漏连续出现。
4. 记忆即将被跨端、跨空间或第三方 Agent 使用。

相同问题已得到稳定反馈后不重复询问。连续出现的“其他类型”达到个人阈值时，系统提议创建自定义类型，而不是自动改变全局分类。

## 7. 个性化规则如何形成

反馈不直接修改原始证据，而是追加事件并派生可撤销规则：

```text
FeedbackEvent
 -> MemoryRevision（这条记忆怎么改）
 -> PersonalMemoryPolicy（以后类似情况怎么处理）
 -> CoverageSnapshot（哪些类型仍然经常漏）
```

规则示例：

- `Work/智能助手` 下生成并通过验证的日报属于“例行产物”，每日合并成一个片段，不拆成十条记忆。
- 文件名含 `prod` 不能自动推断已经上线，必须看到执行证据或等待确认。
- Job 中的明确“发现/结论”可生成发现候选；过期 `STATUS.md` 的状态权重低于最近更新的 Job。
- 个人工作空间中的密钥、原始会话和明细数据永不进入外部 Agent ContextPack。

## 8. R0/MVP 指标

| 指标 | 定义 |
|---|---|
| 每日事件确认覆盖率 | 已确认事件 /（已确认事件 + 用户补充遗漏事件）；只在已复盘时段内报告 |
| 重要记忆确认覆盖率 | 已确认的重要候选 /（已确认的重要候选 + 用户补充的重要遗漏） |
| 重要遗漏率 | 用户补充的重要遗漏 / 同一复盘集合 |
| 候选误报率 | 被标为噪声、重复或不应保存的候选 / 已审候选 |
| 类型覆盖向量 | 每种基础/自定义类型的确认数、遗漏数、来源和最近出现时间 |
| 修正负担 | 每日确认耗时、修改字段数、重复被问次数 |
| 规则复用命中率 | 由既有个人规则自动处理后仍被用户接受的比例 |
| 任务使用价值 | 使用记忆完成真实任务后“有帮助”的次数及缺失原因 |
| 信任事件 | 越权、错误空间、删除失败、来源不可解释等高风险事件 |

小样本阶段只报告人数和原始计数，不用比例包装市场结论。

## 9. 首轮通过条件

FORMALdoc 三天单用户实验只验证专业桌面来源，不计入 15 人用户研究的市场样本，也不能证明普通用户路径。进入通用 DayLedger Prototype 前，至少应看到：

- 每日确认中位数不超过 2 分钟。
- 至少一种不依赖 Git/工作区的通用来源组合可以形成可读的一天。
- 已复盘时段的事件能按时间清晰描述，并能暴露来源缺口。
- 至少 2 条个人规则在后续一天被正确复用。
- 至少 1 个 ContextPack 在真实 Agent 任务中被用户判定有帮助。
- 没有高敏内容在未确认时进入外部模型、Git 或第三方 Agent。
- 系统能明确承认遗漏、来源冲突和过时状态，不把推断写成事实。
