# 目标用户一天上下文覆盖与来源优先级 v0.2

> 文档状态：`in_progress / local_reference_conditional_pass`；用户规模、授权率和真实覆盖增益等待研究回填
> 更新日期：2026-07-26
> 适合读者：产品、设计、研究、客户端、连接器、架构、安全、质量
> 核心用途：决定先覆盖谁的一天、先接哪些来源、每个来源必须补上什么，以及其他模块如何随之调整

## 1. 决策摘要

Ameme 的长期定位是个人记忆系统，不是记录工具。产品需要持续兑现六项承诺：

> **少操作、记得准、找得到、用得上、不丢失、不泄露。**

当前研发主线进一步明确为：

> 先定义目标用户一天中需要保留的上下文，再比较每种来源的目标用户规模、独特上下文增益、可靠性、获取成本和风险；来源先形成可追溯事件，事件稳定后再编译长期记忆并在未来任务中复用。

短期与长期边界：

- 首发切口：AI 使用者中的知识工作者，优先覆盖工作上下文，同时保留 Mobile 独立记录普通一天的能力。
- 产品底座：所有用户共用 `SourceObject → EventCandidate → Event/Revision → DayLedger`，不把核心模型做成会议或 Agent 专用模型。
- 长期方向：按用户生活模式组合 Mobile、Agent、Browser、Communication 和 Life Service 来源包，而不是让所有人开启相同采集器。
- 首版默认不做全天截图、全天录音、全量聊天同步和未经确认的长期人格推断。

## 2. 优先级判断单位

不能用“接入一个来源”作为决策单位。每项候选能力必须明确：

1. 服务哪类目标用户；
2. 补上哪类上下文和哪些字段；
3. 能覆盖多少目标用户以及多少有效 `user-day`；
4. 是自动、场景触发、一次操作、导入还是补缺获取；
5. 来源能够证明什么、不能证明什么；
6. 用户承担多少操作、权限、隐私和社交成本；
7. 能否形成事件并在未来至少一次被有效使用。

### 2.1 两种覆盖不能混为一谈

| 覆盖 | 定义 | 例子 |
|---|---|---|
| 用户覆盖 | 目标用户中有多少人具备平台能力、场景和授权意愿 | 日历对智能手机用户覆盖广；Agent 对首批 AI 用户覆盖集中 |
| 一天覆盖 | 启用来源后能补上多少独特且重要的上下文 | 照片覆盖人多但未必说明结果；Agent 可覆盖较窄人群的大量工作过程 |

### 2.2 规模估算

在首发地区、平台和获客渠道确定前，不使用宏观智能手机人数代替可服务用户规模。每个来源分别估算：

```text
可服务用户规模
= 可触达目标用户
× 平台/账户可用率
× 预计授权率
× 来源在目标场景中的使用率
```

```text
覆盖价值
= 可服务用户规模
× 有效 user-day 频率
× 独特上下文增益
× 事件重建质量
× 未来复用价值
```

```text
相对优先级
= 覆盖价值
÷（用户操作成本 + 工程成本 + 运行成本 + 平台不稳定性）
```

隐私、法律、商店政策、越权、不可删除和不可恢复属于硬门槛，不能通过高覆盖分数抵消。

## 3. 一天上下文分类

| 上下文 | 用户需要记住什么 | 优先证据 | 不能静默推断 |
|---|---|---|---|
| 时间与日程 | 会议、课程、预约、截止时间 | 日历、提醒、用户输入 | 计划是否实际发生 |
| 活动与结果 | 做了什么、完成或改变了什么 | 平台事件、Agent、文件、用户确认 | 业务是否真实完成 |
| 内容消费 | 看过、听过、学过什么 | 分享、Browser、文件、平台 API | 用户是否理解或认同 |
| 内容产出 | 文档、代码、图片、方案和作品 | Agent、文件版本、创作平台 | 产物是否发布或被接受 |
| 沟通与关系 | 与谁交流、讨论了什么 | 会议、邮件、转发、用户补充 | 他人身份、关系和真实意图 |
| 决定与承诺 | 形成了什么选择、谁答应了什么 | 明确原话、会议结论、用户确认 | 普通讨论是否已成为最终决定 |
| 地点与出行 | 去过哪里、如何移动 | 系统建议、事件级位置、票据 | 到访目的和意义 |
| 身体与状态 | 运动、睡眠和获准健康状态 | HealthKit、Health Connect、可穿戴设备 | 医疗判断、情绪和因果 |
| 消费与娱乐 | 购买、游戏、音乐、旅行 | 平台 API、账单导入、分享 | 重要性、满意度和长期偏好 |
| 意图与感受 | 为什么做、是否重要、当时感受 | 用户文字、语音或明确标记 | 不能仅根据行为、健康或位置代替用户表达 |

时间、位置、日程和平台结果适合自动获得。意图、意义、感受以及许多决定和结果只能通过用户的一句话或确认低成本获得。

## 4. 获取方式优先顺序

1. **授权后自动获取**：仅用于范围稳定、事实边界明确的结构化来源。
2. **高确定性场景触发**：会议、任务完成、运动结束、照片聚集等场景生成候选，不直接宣布为事实。
3. **一次操作获取**：分享、选择、按下语音或要求 Agent 记录，保留强意图信号。
4. **导入或转发**：用于封闭平台、历史数据和高敏信息，先本地解析与预览。
5. **补缺提问**：只询问高价值且无法从证据得到的结果、意义和遗漏，允许跳过。
6. **用户明确开启的持续采集**：只在前述方式无法满足已验证场景时考虑；必须可见、可暂停、可排除、限期保存。

无感不等于隐身。任何自动来源都必须在产品中显示采集状态、范围、保存位置和关闭后的处理结果。

## 5. 目标用户优先级

| 层级 | 用户群 | 首要遗忘损失 | 主要来源组合 | 决策 |
|---|---|---|---|---|
| T0 首发 | AI 使用者中的知识工作者 | 项目过程、决定、产物和 Agent 上下文断裂 | Agent + Mobile 主动记录/分享 + 日历 | 使用现有工程基础最快验证“覆盖—编译—复用”闭环 |
| T1 扩展 | 管理者、销售、顾问 | 对话、承诺、客户和会议延续性 | 日历 + 会议/邮件 + Mobile | 复用价值高，但他人数据和组织权限更复杂 |
| T1 扩展 | 学生、创作者、自由职业者 | 学习路径、素材来源、项目演变 | Browser/文件 + Agent + Mobile | 分享和文件路径通用，适合扩展非编码用户 |
| T2 扩展 | 生活记录者 | 生活时刻、人物和旅行遗失 | Mobile + 照片候选 + 日历 + 位置 | 用户规模广，需要更强情绪表达、备份和长期信任 |
| T2 垂直 | 自我量化和游戏用户 | 状态趋势、高光和阶段变化 | Health/Life Service Connector + Mobile | 单一来源覆盖较窄，但垂直上下文增益高 |

T0 是获客与验证顺序，不是产品边界。所有 T0 能力必须允许一个不使用 Agent 的 Mobile 用户独立记录、查看、修订、删除和导出事件。

## 6. 来源与系统能力优先级

### P0：产品成立与长期信任门

| 能力 | 覆盖作用 | 当前基础 | 必须补齐 |
|---|---|---|---|
| 文字、短语音、照片/文件、Share | 所有用户的兜底来源和强意图信号 | 双端主路径已实现 | 真机、失败恢复、来源解释和处理质量 |
| Agent Skill/MCP | 首批用户的高密度工作上下文 | 六模式、授权内读写和本地 Host 已形成 | 真实宿主验证；写入类型边界见第 8 节 |
| 日历只读候选 | 广覆盖的时间骨架 | Android 适配与合成验证已有 | iOS/Android 真机、计划与实际发生分离 |
| Event 编译与 DayLedger | 把碎片变成一天，而非记录列表 | Event/Revision/Today/Summary 已有 | 跨源归并、置信、缺口、候选确认和摘要重算 |
| 来源、Revision、级联删除 | 兑现“记得准、不泄露” | SourceLocator、Revision 和删除路径已有 | 完整 lineage、派生物/备份删除证明 |
| 导出、备份健康和恢复演练 | 兑现“不丢失、可迁移” | 结构化导出/恢复已有 | 明确恢复点、自动备份策略、完整性校验和实际恢复证据 |
| 基础找回与一次复用 | 验证记忆不是只被保存 | Today/Search/Context 已有 | 真实任务复用反馈和来源引用 |

P0 的退出条件不是接入来源数量，而是目标用户可以用少量来源完成：

```text
获得上下文 → 形成可信事件 → 低成本修订
→ 之后成功找回或被 Agent 使用 → 可删除、可导出、可恢复
```

### P1：提高一天覆盖和首发差异化

- iOS Journaling Suggestions、照片时间聚类和 Android 等价候选组合；
- Browser `activeTab` 一键保存、选中文本和来源位置；
- 高确定性任务/会议结束触发，但默认生成候选；
- 人物、项目实体和保守的实体消歧；
- 决定、承诺、未解决问题的分类提取；
- `valid_from`、`valid_to`、`superseded_by`、确认状态与冲突提示；
- 会前/重新打开项目时的可解释记忆浮现；
- 原始证据短期、结构化长期的生命周期策略。

### P2：扩大人群和纵向场景

- 邮件、会议、组织认可的 IM；
- 事件级位置、健康摘要和可穿戴设备；
- 游戏、音乐、出行、消费等垂直 Connector；
- People、Projects 和跨周期回顾；
- 多设备 E2EE 或用户自有存储备份；
- 按项目、人物、时间、数据类型细分的 Agent 只读授权；
- 个性化询问和来源推荐。

### P3：高风险、高成本和平台阶段

- 全天屏幕、全天音频和完整数字生活缓存；
- 全量跨设备原始媒体同步；
- Agent 外部行动；
- 开放 Connector/插件生态；
- 复杂长期人生分析和自动人格判断。

P3 只有在 P0/P1 已证明主动与场景触发无法满足一个高价值场景、用户明确愿意授权且成本可承受时才能进入。

## 7. 六项承诺对应的阶段门

| 承诺 | P0 可接受门槛 | 后续增强 |
|---|---|---|
| 少操作 | 一次分享/一句话；只问高价值缺口；允许稀疏日 | 个性化自动化和场景触发 |
| 记得准 | 原始与 AI 分离；字段证据；候选、确认、Revision | 实体消歧、冲突和有效期 |
| 找得到 | 时间、关键词、来源和基础语义找回 | 人物、项目和变化查询 |
| 用得上 | 至少一次真实搜索或 Agent 任务复用 | 会前、项目和承诺主动浮现 |
| 不丢失 | 本地事务、完整导出、备份状态和恢复演练 | E2EE/用户自有存储、多设备灾难恢复 |
| 不泄露 | 分项权限、空间隔离、加密、删除和访问审计 | 更细 Grant、异常检测和企业控制 |

任何 P0 信任门失败均不得用覆盖率、留存或模型准确率抵消。

## 8. 对现有模块的变更判断

### 8.1 保持不变

- `Event/Revision/DayLedger` 继续作为事实主链，Summary 和 Memory 不覆盖事实。
- Mobile `今天` 继续作为唯一默认主页；搜索是统一历史入口。
- Agent 与 Native Mobile 继续承担双主入口，但来源优先级由覆盖证据决定。
- Local-first、空间隔离、SourceLocator、最小权限和删除传播继续作为默认边界。
- 数据稀疏是合法状态，不通过制造事件提高表面覆盖。

### 8.2 必须调整

**产品与研究**

- 新增“目标用户 × 上下文 × 来源 × 获取方式 × 覆盖增益 × 成本/风险”覆盖矩阵。
- Onboarding 从展示功能改为识别用户的一天发生在哪里，再推荐最小来源组合。
- 首发用户研究必须包含连续 7 天人工回顾，作为来源覆盖的对照基线。

**Today 与交互**

- 区分正式事件、待确认候选和可解释的上下文缺口。
- 显示“当前主要覆盖哪些来源、哪些可能缺失”，不展示虚假精确的全天覆盖百分比。
- 只对重要且不确定的缺口提问。

**编译与数据**

- 增加 `SourceCapability`、`CoverageObservation` 和 `ContextGap` 概念；它们描述来源能力和缺口，不升级为 Memory。
- 逐步增加 Memory、Decision、Commitment 的有效期、替代关系、确认状态和证据链。
- 建立 Raw/Observation/Event/Memory/Index 分层生命周期，索引可重建。

**备份与恢复**

- 当前“本地有控制权但全设备丢失后无法恢复”不满足长期个人记忆定位。
- P0 先完成可验证的本地导出、备份健康和恢复演练；P2 前必须选择 E2EE 云备份或用户自有存储路线。
- 身份服务不保存用户明文记忆的原则可以保留，但不能把“无数据云”误写成“不会丢失”。

**Agent**

- exact Grant 内可以自动创建 Event、EventCandidate 或 Revision，并保留来源和审计。
- Agent 不得自动把推断升级为已确认的长期偏好、关系、健康、财务或重大决定。
- 只读、写候选和外部行动继续分层；外部行动单独确认。
- 知识库内容始终作为数据处理，不能提升为指令或扩大工具权限。

**指标**

- 早期继续使用“一天还原有用率”和“低负担价值日”验证覆盖基础。
- 增加每种来源的独特事件增量、重要遗漏、授权后覆盖提升、单位操作覆盖价值和单位成本。
- 历史积累足够后，将“每周每活跃用户被确认有帮助的记忆复用次数”作为长期北极星候选。

## 9. 执行路线

### R0：覆盖地图与基线

- 对 T0/T1/T2 各类用户进行连续 7 天人工回顾；
- 建立上下文和来源对照表；
- 记录来源可用率、授权意愿、重要遗漏和用户操作；
- 不使用 Event 数或采集字节代表覆盖。

### R1：P0 闭环收口

- 用当前 Mobile、Agent、Share、日历和合成/真实样本跑通覆盖—编译—修订—复用；
- 补齐备份健康、恢复演练、lineage 删除和真实宿主/真机门；
- 为每个来源建立能力、证据和权限声明。

### R2：最小来源组合实验

至少比较：

1. 主动记录；
2. 主动记录 + 日历/照片候选；
3. 主动记录 + Agent；
4. 主动记录 + 日历/照片 + Agent；
5. 按用户类型增加一个 Browser、Communication 或 Life Service 来源。

输出每类用户的最小充分来源组合，而不是统一默认开启清单。

### R3：复用与扩人群

- 首先验证会前、项目恢复、历史搜索和承诺找回；
- 只有真实复用成立后才扩大高敏来源；
- 按边际用户覆盖和独特 user-day 增益选择下一个 Connector。

### R4：长期个人记忆

- 形成带有效期、冲突、替代和权限的长期记忆；
- 完成可验证灾难恢复和服务退出迁移；
- 建立人物、项目、跨周期回顾和可解释主动浮现；
- 在信任、成本和真实需求成立后评估持续采集。

## 10. 下一确认门

启动来源扩张前需要确认：

1. T0 是否继续锁定为 AI 使用者中的知识工作者；
2. 首发地区、iOS/Android 比例和可触达渠道，用于估算真实可服务用户规模；
3. P0 恢复路线先采用用户自有存储，还是进入 E2EE 云备份 Spike；
4. 连续 7 天覆盖研究的参与者、隐私授权和数据删除安排。

在这些输入回填前，本文件中的层级是产品决策优先级，不是已经验证的市场规模结论。

## 11. 2026-07-26 本地执行证据

当前已关闭仓库内可验证的 R0/R1 reference 子门：

- 建立 5 个目标分群、10 类上下文、10 种来源能力和 3 个合成 user-day；
- 增加 `SourceCapability`、`CoverageObservation`、`ContextGap` 严格契约和 4,262 项校验；
- 保守编译输出 8 个证据观测、5 个候选和 6 个显式缺口，不输出全天覆盖百分比，市场规模状态固定为 `not_verified`；
- Core reference 证明计划不升级、照片不推断活动、弱推断不成事件、稀疏时间不造事实；
- 分离“只删除 Raw 证据并保留结构化记录”和“删除来源并沿 lineage 级联”两种用户意图；
- 备份 reference 证明一致 SQLite 快照、Raw 密文 hash、损坏拒绝、无密钥和只恢复到新目录；
- Agent exact Grant 写 Event/Revision 与确认长期 Memory 分离；推断、偏好、关系、健康、财务和重大决定需要用户确认；
- 已验证 Event 可在重启后的后续任务进入 ContextPack，并记录有用反馈；
- 统一工作区 14/14 Gate 通过。

研究执行方案见 `../../research/coverage/目标用户一天上下文覆盖研究执行基线.md`，完整失败历史与边界见 `../quality/P0-上下文覆盖与长期记忆闭环验证-20260726.md`。这些结果只支持 `conditional_pass`，不关闭第 10 节四个外部门。
