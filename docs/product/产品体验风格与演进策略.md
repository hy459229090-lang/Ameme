# Ameme 产品体验风格与演进策略 v0.4

> 文档状态：MVP 效率风格、低保真语义骨架与双端原生 UI 优先原则已确认\
> 更新日期：2026-07-13\
> 当前范围：定义体验性格、信息表达和演进边界；不在本阶段确定品牌名、具体色值、字体、图标或动效参数。

## 1. 当前决策

Ameme 使用同一套 Personal Event Core 支撑两种体验方向：

1. **效率风格**：帮助用户快速看清今天、补齐遗漏、核验来源，并把记录用于后续任务。
2. **情绪风格**：帮助用户重新感受一天中的时刻、关系和情绪，以更温和、更具叙事性的方式回顾生活。

MVP 只实现效率风格。情绪风格不作为第二套数据模型或第二个 App，而是后续可增加的体验表达层。iOS 与 Android 不追求像素一致：统一信息语义、状态和任务路径，各自优先使用系统原生控件、导航、手势、字体和辅助功能。

## 2. 两种风格对应的首要任务

| 方向 | 主要用户动机 | 首要问题 | 主输出重点 |
|---|---|---|---|
| 效率风格 | 信息很多、工作和生活切换频繁、已经使用 AI | 今天发生了什么，有什么遗漏，之后怎样找回和使用 | 清晰事件、状态、来源、补充、找回和 Agent 使用 |
| 情绪风格 | 希望记录生活、关系、感受和有意义时刻 | 今天什么值得记住，当时是什么感受，这段经历意味着什么 | 照片、人物、情绪、关系、叙事和回忆 |

这不是永久用户分群。一个用户可以在工作日偏向效率，在旅行、家庭或回忆场景偏向情绪；体验风格不能与 Work/Personal/Health 等权限空间绑定。

## 3. MVP 效率风格

### 体验性格

`安静、清楚、可信、紧凑、快速，但不冰冷。`

- 安静：不催用户写日记，不用高频提醒制造负担。
- 清楚：用户几秒内知道今天记录了什么、哪里不确定、哪里遗漏。
- 可信：事实、推断、来源、同步状态和修改入口可渐进查看。
- 紧凑：以可扫读事件为主，不把首页做成长篇 AI 日报。
- 快速：补充、确认、纠错和调用尽量一次点击或一句话完成。
- 不冰冷：允许照片、人物和一句用户原话进入事件卡，但不牺牲信息结构。

### 信息层级

```text
今天的整体状态
 -> 按时间排列的事件
 -> 少量待补充或待核验项
 -> 一键照片 / 语音 / 文字补充
 -> 来源、Revision 和权限详情
```

首屏先回答“发生了什么”，效率指标、趋势判断和 AI 建议不抢占主层级。

### 视觉与文案约束

- 基础界面优先采用 iOS SwiftUI 系统组件和 Android Jetpack Compose Material 3 组件，不建立跨平台自定义控件皮肤。
- 使用系统字体、系统图标、语义颜色、原生搜索/列表/日期选择/Sheet/返回手势；品牌只保留有限强调色和内容表达。
- 卡片密度允许高于传统日记，但必须保留呼吸感、清晰时间顺序和足够点击区域。
- 状态通过文字和一致的图形语义表达，不能只靠颜色区分。
- 文案优先使用具体动作和结果，例如“修改了方案”“完成一次跑步”“和朋友吃饭”。
- 不使用“今日效率 8/10”“你浪费了 2 小时”等未经用户选择的绩效化评价。
- 不把工作事件自动写成任务管理器，也不把生活事件强行解释为生产力。

## 4. 后续情绪风格

情绪风格不是给效率界面换一套暖色主题，它会改变信息优先级和阅读节奏：

- 照片、人物、用户原话和有意义时刻优先于来源状态。
- 按“片段”和“故事”组织回顾，允许更慢的浏览节奏和更强的叙事。
- 情绪与关系信息由用户表达或充分证据支持，不为了营造氛围制造心理判断。
- 事实来源、置信状态、Revision 和权限仍然存在，只在默认界面中更渐进地展开。
- 情绪视图不能改写底层 Event，也不能产生与效率视图冲突的另一份真相。

情绪风格进入版本规划前，需要单独验证用户是谁、在什么时刻打开、愿意补充什么，以及是否形成持续价值。

## 5. 现在必须预留的产品边界

| 层 | 共用内容 | 允许变化 |
|---|---|---|
| 数据与权限 | Event、Episode、DayLedger、Revision、来源、空间、保留和删除 | 不因风格改变 |
| 信息语义 | 事实、情绪、关系、重要性、媒体和用户原话 | 不同风格调整默认显隐和排序 |
| 组件语义 | 事件卡、日期段、补充入口、状态、来源详情 | 布局、密度、媒体比例和叙事方式 |
| 设计系统 | 可访问性、语义状态、平台原生组件行为 | 品牌强调、媒体比例和少量产品特征；不强制两端像素一致 |
| 用户偏好 | 同一个账户和事件集合 | 后续可按场景选择效率/情绪体验，不绑定权限空间 |

实现时不急于加入数据库级 `style` 字段；先让展示层和设计 Token 可替换，并保持领域对象使用中性语言。

## 6. 对 Mobile 信息架构的直接影响

MVP 的 `今天` 页面按效率风格设计：

- 核心是事件时间线，而不是 AI 生成的大段总结。
- 照片和用户原话作为事件证据和记忆温度存在，不做装饰瀑布流。
- 待补充只展示少量高价值缺口，不形成审核任务列表。
- 语音、照片、文字和上传补充在 `今天` 的低成本位置可达。
- `今天` 右上放大镜按钮进入日历 + 关键词组成的历史搜索页；来源控制和权限管理进入平台原生设置二级入口，不挤占主视图。

## 7. MVP 风格验收标准

1. 新用户能在数秒内看懂 `今天` 页面的主任务。
2. 用户能一次操作补充一件事，且不需要理解 Event、DayLedger 或 MCP。
3. 页面既能容纳工作事件，也能自然显示吃饭、运动、照片和关系事件。
4. 事实、推断和待核验状态可辨认，来源和权限可找到。
5. 整体感受是“帮我整理”，而不是“监控我”或“考核我”。
6. 当前组件和领域语义不会阻断后续情绪风格。

## 8. 后续设计顺序

1. 依据已选 `今天` 页骨架补齐搜索页、事件详情、权限旅程和关键状态低保真。
2. 用页面模块—数据对象—来源状态映射检查界面能否被真实数据支撑。
3. 分别形成 iOS 与 Android 原生组件映射和可交互骨架，验证导航、搜索、日期、补充和设置的流畅性。
4. 在系统组件之上确定有限的品牌强调 Token、事件表达和媒体语言，不重新设计基础控件。
5. 用合成的一天验证信息密度、获取、补充、纠错、来源解释和空状态。
6. 情绪风格在 MVP 价值成立后单独立项和验证。
