# Ameme 移动端来源与轻量位置记录 v0.3

> 文档状态：A0-A3 机会式位置级联与五类健康授权包已确认；原始点位保留时间待双端实测\
> 更新日期：2026-07-13\
> 适用范围：iOS 与 Android Native Mobile MVP\
> 目标：用照片、语音、位置和获准手机数据覆盖日常事件，同时控制电量、精度、隐私和用户打扰。

## 1. Mobile 来源优先级

| 优先级 | 来源 | 产品作用 | 原始数据默认值 |
|---:|---|---|---|
| 1 | 照片 | 现场、人物、时间、地点和生活时刻的最丰富证据 | 原图默认留在设备/系统照片库，Ameme 保存引用、缩略或用户选择内容 |
| 2 | 语音记录 | 补充意图、感受、意义和没有数字痕迹的事件 | 优先保存转写与来源；原始音频是否长期保留由用户选择 |
| 3 | 轻量位置 | 形成到访、通勤、出行和旅行的时间/地点骨架 | 原始点位只在本地短期缓冲，长期保存事件化地点 |
| 4 | 日历 | 提供计划、会议、地点和时间锚点 | 结构化字段按空间策略同步 |
| 5 | 健康活动摘要 | 补充步数、锻炼和睡眠等身体活动事件 | 独立 Health 空间，结构化摘要优先，不同步医疗原始数据 |
| 6 | 文字、分享和文件 | 接收用户主动表达及其他 App 对象 | 按对象和空间保存 |

信息源优先级不等于事件重要性。照片是高价值来源，但一张重复截图可以是低权重信号；一句用户语音可能成为当天最高权重事件。

## 2. 轻量位置的产品定义

位置能力的目标不是画一条全天 GPS 轨迹，而是回答：

- 用户什么时候到达或离开一个有意义地点？
- 一段时间是在通勤、旅行还是停留？
- 照片、日历、语音和现实活动是否属于同一事件？

长期保存对象应是 `PlaceVisit`、`TripSegment` 和 Event 字段，而不是无限增长的坐标点列表。

## 3. 机会式位置级联

默认策略不是固定频率定位，而是逐级使用“当前已有且足够”的最低成本信号：

```text
已有授权数据
 -> 系统被动位置事件
 -> 用户动作时单次定位
 -> 必要时短时高精度
```

### A0：复用已有授权数据

- 优先使用照片 EXIF、日历地点、地图分享、系统 Journaling Suggestions、获准的锻炼路线和用户已有地点标签。
- 这些信息足以说明事件地点时，不额外唤起定位。

### A1：订阅系统被动事件

- iOS 使用 Visit、显著位置变化和系统区域事件。
- Android 使用 Geofencing、Passive Location、低功耗 Fused Location 和可用的活动转换信号。
- 只消费操作系统已经形成或低功耗维护的到达、离开和明显移动信号，不连续采样 GPS。

### A2：用户动作时单次定位

- 用户拍照、语音、分享、打开 `今天` 或手动补充事件时，如果 A0/A1 无法提供足够地点信息，再请求一次近似位置。
- 本次动作完成或超时后立即停止。

### A3：必要时短时高精度

- 仅在用户主动记录路线、地点存在歧义或明确要求精确地点时短时启用。
- 必须有可见状态、超时和自动停止，不作为全天后台模式。

## 4. 渐进授权

### L0：不申请位置权限

- 使用用户选择照片的 EXIF、日历地点和分享对象。
- iOS 可让用户主动打开 Journaling Suggestions 选择包含到访地点的系统建议；只有用户选择后，应用获得高层信息。
- 用户仍可手动给事件添加地点。

### L1：记录当下位置

- 用户拍照、语音、分享或主动记录时，请求“使用 App 时”或单次位置。
- 优先接受系统提供的近似位置；只有用户明确需要精确地点时才提升精度。
- 一次事件结束后停止主动定位。

### L2：自动形成到访事件

- 用户已经看到位置补全事件的价值后，再单独说明并申请后台位置能力。
- iOS 使用系统的 Visit、显著位置变化或区域事件；Android 使用地理围栏、被动位置和低功耗 Fused Location。
- 后台只生成到达、离开、停留和移动片段，不请求持续高精度轨迹。
- 拒绝 L2 不影响照片、语音、“我的一天”和其他 Mobile 能力。

### L3：临时精确路线

不进入 MVP 默认路径。未来只有旅行、运动或用户手动开始的特定场景才允许，并提供持续状态指示和自动停止。

用户可以在理解用途后直接主动开启 L2，不必强制依次经历 L0/L1。授权等级规定系统最多能做什么，A0-A3 机会式级联决定每次实际使用哪种最低成本来源。

## 5. 双平台实施边界

### iOS

- Journaling Suggestions 在系统选择器中展示近期个人事件；应用只在用户选中建议后得到高层信息，适合作为低权限补充入口。[Apple Journaling Suggestions](https://developer.apple.com/documentation/JournalingSuggestions)
- Journaling Suggestions 的 Location 代表一次到访，系统在用户选择后才提供给应用。[JournalingSuggestion.Location](https://developer.apple.com/documentation/journalingsuggestions/journalingsuggestion/location)
- Core Location 提供 Visit 和显著位置变化服务；Visit 可使用降低精度的位置，显著位置变化只在明显移动后产生更新。[Visit monitoring](https://developer.apple.com/documentation/corelocation/cllocationmanager/startmonitoringvisits%28%29)、[Significant-change monitoring](https://developer.apple.com/documentation/corelocation/cllocationmanager/startmonitoringsignificantlocationchanges%28%29)
- Location 必须先提供清楚用途说明；后台能力需要额外说明和适当授权，不能在首次启动无上下文索取。[Apple location authorization](https://developer.apple.com/documentation/corelocation/requesting-authorization-to-use-location-services)

### Android

- Android 区分前台/后台及近似/精确位置；用户只给近似位置时，应用必须仍可工作。后台位置只适用于核心功能，并受 Play 政策约束。[Android location permissions](https://developer.android.com/develop/sensors-and-location/location/permissions)
- Android 11 及以上的后台位置通常需要用户进入系统设置开启，产品必须先提供解释，并允许拒绝后继续使用。[Android background permission](https://developer.android.com/develop/sensors-and-location/location/permissions/background)
- 后台位置会被系统限频；Geofencing 建立在 Fused Location 之上并针对电量优化，适合到访事件而非连续轨迹。[Background location and battery](https://developer.android.com/develop/sensors-and-location/location/battery)、[Android geofencing](https://developer.android.com/develop/sensors-and-location/location/geofencing)
- 被动位置优先使用无额外功耗或低功耗模式；持续后台不使用高精度请求。[Android location scenarios](https://developer.android.com/develop/sensors-and-location/location/battery/scenarios)

平台能力存在差异，因此 MVP 验收“能形成可信到访/移动事件”，不要求两个系统产生完全相同数量和精度的点位。

## 6. 位置事件化流程

```text
LocationSignal（短期本地点位）
 -> 去噪和精度分级
 -> 停留聚类 / 移动分段
 -> PlaceVisit / TripSegment 候选
 -> 与照片、日历、语音和 Agent 时间合并
 -> Event / Episode
 -> 原始点位按保留策略滚动删除
```

事件化规则：

- 单个点位不是 Event。
- 同一地点的抖动合并，不生成重复到访。
- 用户主动拍照/语音时的地点可提升该事件的时间和地点置信度。
- 地点名称可以保存为城市、区域或用户标签；精确坐标不是长期展示默认值。
- 家、医疗机构、宗教场所等敏感地点优先使用本地标签和更高敏感度，不自动进入 Agent ContextPack。
- 位置与照片、日历冲突时保留冲突，不强行覆盖。

## 7. 电量和资源策略

- 静止状态不持续请求定位。
- 照片、日历、锻炼或系统到访事件已经足够时，不再发起位置请求。
- 后台优先系统 Visit、显著变化、地理围栏、被动或低功耗批处理。
- 只有用户主动记录时进行一次即时位置获取。
- 每个位置会话有停止条件和超时。
- 设置页显示近 24 小时位置事件数量、最近采集时间和电量影响等级；具体电量阈值在双端 Spike 中测量。

## 8. 照片与语音处理边界

### 照片

- 先用时间、EXIF、相册分组和用户选择范围形成候选，再按需进行端侧或获准云端视觉理解。
- 连拍、同地点和短时间照片先聚合为一个候选，不把每张照片当事件。
- 默认不复制完整照片库；结构化事件和用户选择的照片只按空间同步到已批准 LAN peer。
- 人物关系不能仅靠人脸识别推断，人物与关系由用户补充或明确授权来源确认。

### 语音

- 核心操作是一键开始、一键结束或按住说；保存后立即显示转写和所指时间。
- 语音内容拆分为事实、意图、感受和重要性，不让模型把情绪语气当成确定事实。
- 优先端侧转写；需要云端时显示处理位置并允许只上传当前片段。
- 原始音频与转写拥有独立保留期，删除音频不必删除用户确认后的文字事件。

## 9. 健康信息边界

- 产品使用同一条“身体与活动”交互路径说明价值和权限，用户可以在一个页面看到并选择五个数据包：

| 授权包 | 候选数据 | 形成的事件或背景 |
|---|---|---|
| 日常活动 | 步数、步行/跑步距离、活动时长、活动能量、站立/楼层（平台可用时） | 散步、长时间活动、低活动日等日常片段 |
| 锻炼 | 类型、开始/结束、时长、距离、能量、可选路线 | 跑步、骑行、健身、球类等明确事件 |
| 睡眠 | 入睡/醒来区间、时长、阶段（来源可用时） | 睡眠事件和当天身体背景 |
| 恢复 | 静息心率、心率变异性、呼吸率等日级摘要 | 只作为恢复背景或待核验变化，不直接诊断健康状态 |
| 正念/主观状态 | 正念会话、用户主动记录的身体或情绪状态 | 冥想、放松和用户主动表达事件 |

- iOS HealthKit 与 Android Health Connect 都按数据类型授权；产品可以把数据包放在一条体验路径中，但系统实现仍需逐类型申请，并让用户按包增减。[Apple HealthKit authorization](https://developer.apple.com/documentation/HealthKit/authorizing-access-to-health-data)、[Android Health Connect permissions](https://developer.android.com/health-and-fitness/health-connect/ui/permissions)
- MVP 默认推荐日常活动、锻炼和睡眠三个包；恢复和正念/主观状态作为同页可选扩展。HealthKit 与 Health Connect 均提供活动、锻炼、睡眠、生命体征和正念类数据类型。[Apple HealthKit category types](https://developer.apple.com/documentation/healthkit/hkcategorytypeidentifier)、[Apple HealthKit quantity types](https://developer.apple.com/documentation/healthkit/hkquantitytypeidentifier)、[Apple HKWorkout](https://developer.apple.com/documentation/healthkit/hkworkout)、[Android Health Connect data types](https://developer.android.com/health-and-fitness/health-connect/data-types)
- 临床记录、疾病、用药、生殖健康、血压和血糖不进入 MVP 默认授权；原始心率流也不默认读取。
- Health 数据进入独立空间，默认不用于 Work 效率、情绪推断或第三方 Agent。
- Android 后台读取需要额外权限；没有后台权限时在前台或系统允许时同步，不降低其他功能。[Android Health Connect read data](https://developer.android.com/health-and-fitness/health-connect/read-data)
- Google Play 要求健康权限与明确的用户可见功能对应、只申请必要范围并提供透明控制，因此“一条交互路径”不等于一次获取全部健康权限。[Google Play Health Connect policy](https://support.google.com/googleplay/android-developer/answer/17105854)
- HealthKit 对读取授权有隐私保护，应用不能把“没有返回数据”解释成用户没有该活动或健康记录。

## 10. 情绪、关系与重要性的条件使用

- 用户明确表达的情绪可以支持“事件发生在本人身上”和“这件事对用户的意义”等直接字段；人脸、声纹或健康波动只形成待核验候选。
- 用户说明的关系或共同事件可以支持参与人字段；联系频率只能形成弱候选，不能单独定义关系类型或好坏。
- 情绪、关系和重要性不提高任何事实字段置信度；它们只用于表达、排序和回顾，也不得触发授权扩大。
- 用户标记“这件事很重要”时，可以进入一次明确的跨空间或第三方 Agent 授权流程。用户确认对象、用途、接收方和有效期后形成可撤销规则，不静默绕过权限。

## 11. 已收口规则与实现验证

1. 解释页可以提供“开启更完整的到访记录”显式动作，但只在说明价值、电量、读取时机和关闭方式后进入平台原生授权；拒绝后保持 A0/A1 可用，不把 L2 设为进入产品的权限墙。
2. 原始位置点采用本地短期滚动恢复缓冲；具体 TTL 由 LOC/RAW 双端实测回填。
3. 长期结构化默认只保存满足事件需要的区域/地点标签、时间范围和精度，不保存精确连续轨迹；用户明确保留的单次地点证据另按对象处理。
4. 照片原图和语音原音频默认留在来源端，结构化事件按同步决策跨端；选定 Raw 逐对象授权。
