# Ameme 事件反馈与记忆类型模型 v0.3

> 文档状态：架构草案，等待 FORMALdoc 单用户实验验证\
> 目标：先让 EventCandidate/DayLedger 可补漏和修订，再让记忆类型可扩展、反馈可追溯、个性化规则可撤销。

## 1. 新增领域对象

| 对象 | 职责 | 是否可变 |
|---|---|---|
| `EventCandidate` | 从一个或多个信号生成的事件草稿 | 通过 EventRevision 演进 |
| `EventRevision` | 保存事件时间、描述、主体、结果和来源修订 | 只追加 |
| `DayLedger` | 组织某天的事件、片段、来源和覆盖缺口 | 通过 Revision/重算演进 |
| `MemoryTypeDefinition` | 定义基础或个人自定义记忆类型、版本和父类型 | 版本化，不原地覆盖 |
| `MemoryCandidate` | 从可信 Event/Episode 中提炼的待确认长期记忆 | 通过 Revision 演进 |
| `MemoryRevision` | 保存用户/系统对候选或记忆的每次变更 | 只追加 |
| `FeedbackEvent` | 记录确认、纠错、遗漏、类型、空间、使用结果等反馈 | 只追加，可撤销其影响 |
| `PersonalMemoryPolicy` | 从重复反馈中派生的个人规则 | 可暂停、修改、删除 |
| `CoverageSnapshot` | 按时间、空间、来源和类型保存覆盖/遗漏统计 | 可重算 |

原始 `SourceObject`、`Observation`、`Event`、`Episode` 和 `LineageEdge` 继续作为证据层。Summary 是 DayLedger 的派生展示，不进入证据层。反馈不能改写历史对象，只能产生新的 Revision 或 Policy。

## 2. 类型模型

记忆类型为多标签：

```json
{
  "type_id": "decision",
  "scope": "base",
  "version": 1,
  "display_name": "决策与理由",
  "parent_type_id": null,
  "status": "active",
  "created_by": "system",
  "sensitivity_default": "normal"
}
```

个人自定义类型必须指向一个最接近的基础类型或明确为 `unmapped`。模型可以提议类型，只有用户确认后才创建个人类型。

## 3. 事件草稿必须携带不确定性

```json
{
  "event_candidate_id": "ec_20260713_001",
  "space_id": "work",
  "title": "补齐多日智能助手日报与 Session 明细",
  "semantic_labels": [
    {"label": "work", "confidence": 0.88},
    {"label": "artifact_change", "confidence": 0.74}
  ],
  "occurred_at": {"start": "2026-07-13T10:11:00+08:00", "end": "2026-07-13T10:58:00+08:00"},
  "fact_confidence": 0.72,
  "freshness": {
    "latest_evidence_at": "2026-07-13T10:57:08+08:00",
    "conflicting_sources": []
  },
  "lineage_edge_ids": ["le_1", "le_2"],
  "status": "candidate"
}
```

事件草稿先回答“可能发生了什么”，不要求此时判断是否值得长期记忆。文件名中出现 `prod`、`ship`、`done` 只能作为低到中置信信号，不能直接形成“已上线/已完成”事实。状态事实需要执行结果、当前 Job、远端回读或用户确认。

## 4. FeedbackEvent

### 4.1 动作集合

| action | 含义 |
|---|---|
| `accept` | 接受当前事件草稿或记忆候选 |
| `reject` | 事件未发生、噪声、重复或不应保存 |
| `correct_field` | 修改事实字段、时间、项目、人物等 |
| `add_missing` | 补充系统未捕获的事件；之后再判断是否形成长期记忆 |
| `relabel_type` | 修改/增加/删除记忆类型 |
| `set_importance` | 设置重要性或高光 |
| `merge` / `split` | 调整片段粒度 |
| `move_space` | 修改所属隔离空间 |
| `set_retention` | 修改保留期和原始内容策略 |
| `set_future_rule` | 指定类似内容以后自动/询问/忽略 |
| `mark_useful` | 在真实任务使用后确认有帮助 |
| `mark_irrelevant` | 内容正确但本次任务不相关 |
| `mark_outdated` | 记忆已过时 |
| `report_missing_context` | 使用时缺少关键上下文 |
| `report_policy_violation` | 出现越权、错空间或不应引用来源 |

### 4.2 事件示例

```json
{
  "feedback_id": "fb_20260713_001",
  "target_type": "event_candidate",
  "target_id": "ec_20260713_001",
  "action": "correct_field",
  "actor": {"type": "user", "id": "local_owner"},
  "payload": {
    "field": "summary",
    "value": "修复日报生成流程并补齐多日缺失产物",
    "reason": "原描述只写了生成文件，没有说明真正发生的事情"
  },
  "purpose": "daily_review",
  "device_id": "desktop_local",
  "space_id": "work",
  "created_at": "2026-07-13T21:30:00+08:00",
  "sync_policy": "structured_only"
}
```

`payload.reason` 可能包含敏感内容，默认只保存在本地；同步时可只发送结构化动作。

## 5. 状态、冲突与新鲜度

事件草稿状态：

```text
candidate -> confirmed -> superseded
       |              |
       v              v
    rejected       revoked
```

每个事实字段都可以记录：

- `observed_at`：信号发生时间。
- `source_updated_at`：来源最后更新时间。
- `source_authority`：该来源对该字段的权威等级。
- `fact_confidence`：当前置信度。
- `conflicts_with`：冲突的对象/字段。
- `confirmed_by` 与 `confirmed_at`：用户或可信系统确认。

权威不是全局固定。例如 Git 对“是否提交”权威，但对“任务是否完成”不权威；Job 对计划状态更权威，但过期的根状态看板应被降权。

## 6. PersonalMemoryPolicy

规则结构至少包含：

```json
{
  "policy_id": "p_work_routine_reports",
  "space_id": "work",
  "match": {
    "source": "filesystem",
    "path_prefix_hash": "...",
    "artifact_family": "daily_report"
  },
  "action": {
    "group_window_minutes": 180,
    "default_type": ["episode", "artifact_milestone"],
    "review_mode": "daily_batch"
  },
  "derived_from_feedback_ids": ["fb_1", "fb_8"],
  "confidence": 0.84,
  "status": "active"
}
```

规则必须显示“为什么形成”、影响哪些来源/空间，并支持暂停或删除。删除规则不删除历史反馈；用户可以另行要求删除相关反馈和派生记忆。

## 7. 本地存储表

首阶段继续使用 SQLite，不引入独立图数据库：

| 表 | 关键字段 |
|---|---|
| `event_candidates` | event_candidate_id、space_id、time_range、fact_fields、confidence、status |
| `event_revisions` | revision_id、target_id、field_patch、actor、created_at |
| `day_ledgers` | date、space_id、event_ids、episode_ids、coverage_gaps、revision |
| `memory_type_definitions` | type_id、scope、owner_id、version、status |
| `memory_candidates` | candidate_id、space_id、title、status、confidence、time_range |
| `memory_candidate_types` | candidate_id、type_id、confidence、source |
| `memory_revisions` | revision_id、target_id、patch、actor、created_at |
| `feedback_events` | feedback_id、target、action、payload、purpose、space_id |
| `personal_memory_policies` | policy_id、match、action、derived_from、status |
| `coverage_snapshots` | date、space_id、type_id、confirmed、missing、rejected、used |

所有表都带 `device_id`、`created_at`、`updated_at`、`sync_policy` 和审计字段。向量/全文索引是可重建派生物，不是反馈或记忆的真相源。

## 8. 隔离、同步和删除

- `FeedbackEvent.space_id` 默认继承目标记忆空间，移动空间产生新事件。
- Work 空间可只同步结构化动作，不同步反馈原文和来源路径。
- Health/Finance 反馈不能被用于生成 Work 效率规则，除非用户单独授权跨用途分析。
- 第三方 Agent 只能通过带 `purpose + spaces + time_range + data_types` 的接口提交使用反馈。
- 删除 SourceObject 时按 lineage 重算候选和覆盖；删除 FeedbackEvent 时重算 Revision、Policy 和 CoverageSnapshot。

## 9. Prototype 最小接口

```text
list_daily_event_candidates(date, spaces)
submit_feedback(target_id, action, payload)
add_missing_event(text_or_source, space, occurred_at)
confirm_day_ledger(date, spaces)
list_personal_policies(space)
generate_context_pack(purpose, spaces, time_range, data_types)
report_context_pack_result(pack_id, outcome, missing_context)
```

接口不允许第三方直接写 `Memory`；新增内容先成为 Candidate，并遵循空间、敏感度和确认策略。

## 10. 双端生产最小长期 Memory 边界

2026-07-26 已在 Android SQLCipher schema v8 与 iOS AES-GCM local-store envelope v3 接入最小非视觉生产切片：

- 类型固定为 `fact/decision/commitment/insight/preference/relationship/health/financial/major_decision`；
- proposal 绑定一个 exact active Event revision，evidence 与 sensitivity 由存储层读取；
- `eligible_for_memory_compiler` 与 `candidate_user_confirmation_required` 都只是候选，只有显式用户确认才能进入 `active`；
- `valid_from/valid_until` 只控制默认可见性，不提高事实置信度；
- replacement 产生 `superseded`，上游 Event revision/delete 产生 `invalidated`，旧终态不能由重编译或重开复活；
- Android Agent Local Node 只开放 Event/Revision 写入；它未获得长期 Memory operation、Grant 或 confirmation repository，Agent Revision 只会使旧 Event-bound Memory 失效。

当前 Android v8 instrumented test 与 iOS XCTest 只完成源码/target 编译准备，未形成设备证据；ContextPack/Recall、UI、跨设备同步、多证据重算、生产恢复和真实用户复用仍是独立 Gate。
