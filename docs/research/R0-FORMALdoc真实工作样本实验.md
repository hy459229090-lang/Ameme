## 0. 重定位说明

FORMALdoc 是专业知识工作者的一种复杂数据源，不是 Ameme 的使用前提。它只验证来源包 B“专业桌面增强来源”。产品核心改为通用 `DayLedger`：不同用户使用不同来源组合，最终都形成同一种每日事件账本。

## 4. 这批事件草稿暴露的来源缺口

| 仅靠现有来源较容易获得 | 仅靠现有来源很难可靠获得 |
|---|---|
| 文件族、时间段、产物路径、脚本/报告关联、当前 Job 描述 | 为什么做、是否真正完成/上线、哪个结论最重要、放弃了什么、谁需要跟进、用户当时的判断变化 |

因此每日事件账本不能只问“这些对不对”，还要先按上午、下午、晚上寻找漏掉的事件，再从可信事件中识别：

1. 决策理由。
2. 发现带来的认知变化。
3. 仍有效的承诺和下一步。
4. 没有产物但很重要的沟通、思考或阻塞。
5. 用户希望系统以后遵守的记录规则和隐私边界。

## 5. 后续事件核验卡（暂不作为下一确认门）

Event/DayLedger Schema 冻结后，参与者可以用自然语言核验发生了什么，不需要选择记忆类型：

```text
C1：发生了 / 改成…… / 没有发生或不记录
C2：发生了 / 改成…… / 没有发生或不记录；是否已上线……
C3：正式部署 / 测试打包 / 没有发生或不记录
C4：发生了 / 改成……；实际结论……
遗漏：上午 / 下午 / 晚上还发生了哪些事……
规则：以后遇到类似内容，希望自动记 / 先问我 / 忽略……
```

这张卡只用于核验专业桌面来源，不承担普通用户体验验证。

## 6. 专业桌面来源三天实验（待 DayLedger Schema 后恢复）

### 第一天：建立基线

- 从低权限元数据生成 3–8 个 EventCandidate，并合并候选 Episode。
- 收集发生/未发生、时间、描述、合并/拆分和时段遗漏；记忆类型不作为必填反馈。
- 根据反馈生成首批个人规则，但保持“待启用”。

### 第二天：验证规则复用

- 用 Day 1 规则合并例行产物、降低旧状态权重、识别新 Job 发现。
- 明示“因为你昨天这样修改，所以今天这样整理”。
- 记录规则是否被接受、是否减少重复确认。

### 第三天：验证真实使用

- 生成一个仅含获准信息的 Work ContextPack。
- 用它完成一个真实 Agent 任务，例如继续某个分析、形成工作复盘或准备下一步计划。
- 收集有用、无关、过时、缺失和越权反馈。

## 7. 实验指标

- 每日确认耗时和操作数。
- 已确认事件、时段遗漏、误报、错序、错误合并和冲突数。
- 已复盘时段的事件覆盖及每类来源带来的覆盖增益。
- 个人规则复用的接受/撤回次数。
- ContextPack 是否减少重新描述，以及缺失了什么。
- 是否发生敏感内容误采、错误空间、不可解释来源或删除失败。

## 8. Gate 影响

本实验只能说明专业桌面来源的能力与噪声，不能凭 1 人通过 Gate 1，也不能证明普通用户会拥有类似工具链。完成后仍需按既定计划进行三个分组的 15 人研究，并单独用不含 Git/工作区的通用来源样本验证 DayLedger。
