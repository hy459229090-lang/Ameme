# Ameme 项目章程 v0.2

更新日期：2026-07-13

## 1. 愿景

构建一个跨设备、跨应用、跨场景的个人事件与记忆层：让用户用接近零操作的方式覆盖一天中有意义的事件，清晰保存发生了什么，再从可信事件中形成总结、回顾和长期记忆。

终局不是“AI 替用户写日记”，而是帮助用户获得四种能力：

- Recall：找回发生过什么。
- Reflect：看懂一段时间内的变化与模式。
- Act：让 AI 基于个人历史提供更合适的建议和行动支持。
- Own：用户真正拥有、控制并能迁移自己的记忆。

## 2. 当前问题定义

用户的数字生活散落在浏览器、文件、代码、IM、会议、照片、位置、账单、健康和游戏记录中。现有工具通常只解决其中一段：采集、日记、搜索或 Agent 记忆，缺少从可信采集到长期理解的完整闭环。

核心链路调整为：

`Signal -> EventCandidate -> Event/Episode -> DayLedger -> Memory/Summary -> Recall/Insight`

其中：

- Signal：原始数字信号，如窗口、文件变动、照片元数据。
- EventCandidate：系统根据碎片信号推测的事件草稿，可以被纠正或丢弃。
- Event：带来源和时间的可核验事实。
- Episode：一段具有共同意图的活动集合。
- DayLedger：按日期组织、保留来源和置信度的每日事件账本，是“这一天发生了什么”的核心记录。
- Memory：可被未来检索和使用的稳定信息。
- Summary：基于事件账本生成的日/周/月表达，可重新生成，不是真相源。
- Insight：跨时间分析得到的模式或建议。

用户纠正贯穿 EventCandidate、DayLedger 和使用结果，用于补漏和纠错，不是产品的第一层价值。

## 3. 必须先验证的假设

### 用户价值

- H1：即使没有 Git、工作区或 Coding Agent，普通用户也能通过手机系统入口、照片、日历、分享和一句话形成有用的每日事件账本。
- H2：不同用户可以使用不同来源组合，但底层都能形成同一种 Event/DayLedger，并在此基础上总结和找回。
- H3：用户能接受受控采集，但不能接受默认无边界录屏、录音或读取私密内容。

### 产品机制

- H4：多来源碎片可以先形成 EventCandidate，再合并为时间有序、描述清楚、来源可查的 DayLedger。
- H5：原始事实、事件草稿、用户确认和总结分层，能避免“摘要替代事实”和错误长期记忆。
- H6：一天中有意义事件的覆盖率、错序率和错误率，比最终文字是否华丽更决定产品价值。

### 商业与成本

- H7：批处理、规则过滤、小模型抽取和增量总结能把 AI 成本控制在订阅收入的合理比例内。
- H8：普通用户更适合按能力档位订阅；API/token 用量只作为 Power/API 套餐的计费维度。

## 4. 首阶段边界

Discovery 阶段不会直接构建全量录屏、录音、IM 抓取或手机账单读取。先完成：

1. 竞品与替代方案调研。
2. 15 位三类目标用户的问题访谈，并先用单用户样本校准协议。
3. 三个 MVP 方案的价值、权限、成本和实现复杂度比较。
4. 选定首批用户、首个核心任务和成功指标。
5. 经确认后再写 PRD、数据结构和技术方案。

## 5. 阶段与确认门

### Gate 1：方向确认

确认首批用户和 MVP 路线。

### Gate 2：方案确认

确认 PRD、隐私模型、Memory Schema、Context Pipeline、成本预算和验证指标。

### Gate 3：原型确认

用可交互原型和模拟数据验证日报、搜索、纠正和授权体验。

### Gate 4：工程实现

实现本地采集器、处理管线、存储、用户界面和 MCP/API 的最小闭环。

### Gate 5：真实试用

在明确的数据边界下进行小规模 dogfood 和用户试用，根据事实决定继续、调整或停止。

## 6. Discovery 成功标准

- 明确一个具体首批用户，而非“所有人”。
- 明确一个每天或每周反复发生、当前解决很差的任务。
- 至少一种低风险数据组合能支撑该任务。
- 能把不同来源还原成清晰、可追溯的每日事件，而不是只生成一段不可核验的总结。
- 用户能理解采集内容、推断来源以及删除方式。
- 初步单位经济模型可成立。
