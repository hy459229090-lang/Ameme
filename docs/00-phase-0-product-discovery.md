# Ameme Phase 0：产品立项与问题验证

更新时间：2026-07-13  
状态：历史调研输入；其中 MVP 建议尚未确认，后续以 `02-product-system-framework.md` 为主框架

## 1. 项目命题

Ameme 不应被定义为“自动写日记的软件”，而应被定义为：

> 一个由用户控制的个人记忆基础设施，低摩擦获取分散在设备和应用中的生活与工作线索，将其整理为可核对、可检索、可复盘、可供 AI 调用的长期上下文。

终局能力包含四层：

1. Capture：从电脑、手机、IM、照片、账单、游戏、会议等来源获得线索。
2. Understand：把原始线索整理成事件、人物、项目、目标、偏好和关系。
3. Remember：形成有来源、有置信度、有生命周期、可纠正的记忆。
4. Reflect & Act：生成日报/周报、发现模式，并在适当时机为其他 AI 提供上下文。

第一版不能同时覆盖四层的全部来源。第一版要验证的核心不是“能采多少”，而是：

> 用户是否相信并持续使用 AI 根据低摩擦线索生成的个人记忆。

## 2. 当前市场版图（截至 2026-07-13）

| 路线 | 代表产品 | 已验证能力 | 主要缺口 | 对 Ameme 的启示 |
|---|---|---|---|---|
| 电脑全量回溯 | Microsoft Recall | 定期屏幕快照、本地索引、自然语言查找、应用/网站过滤、敏感信息过滤 | 更像“找回看过的内容”，不负责形成日记、长期认识或跨端人生模型 | 捕获必须显式可见、可暂停、可过滤、可批量删除 |
| 本地桌面记忆 | screenpipe | 屏幕、无障碍树文本、OCR、音频转写、本地存储、搜索/API | 捕获能力强，但用户价值仍偏搜索和自动化；高质量记忆形成尚未成为清晰产品闭环 | 可借鉴本地采集技术，差异化应放在记忆形成、核对和复盘 |
| 屏幕/对话记忆 | Rewind / Limitless | 对屏幕或现实对话进行捕获、转写、摘要和问答 | 持续录音的社会许可和隐私门槛很高；硬件路线重 | 第一版不应依赖全天录音，会议/对话采集必须有明显状态和同意机制 |
| 主动 AI 日记 | Day One Daily Chat | AI 追问、把对话整理成可编辑日记、加密保存 | 仍需要用户主动开启和回答；上下文主要来自用户表达 | 用户确认是价值环节，但应压缩成“核对/修正”，而不是重新叙述一天 |
| 手机事件建议 | Apple Journaling Suggestions | 系统根据照片、地点、联系人、运动、媒体等生成建议；用户选择后才向应用披露 | iOS 生态内、用户选择后才共享，不是第三方后台全量采集 | 普通用户的“一键记录”可基于系统建议，而不是索取所有底层权限 |
| Agent 记忆基础设施 | Mem0、Zep 等 | 为应用提供用户/会话记忆抽取与召回 | 主要处理已经进入 AI 会话的数据，不解决现实世界上下文采集与用户日记闭环 | Ameme 后期可提供 MCP/API，但首版不能只做开发者 SDK |

## 3. 市场空白判断

市场已经分别证明了五件事：屏幕可以持续捕获，音频可以转写，手机可以提出生活事件，AI 可以辅助日记表达，Agent 可以读取结构化记忆。

仍未被完整解决的是中间层：

> 如何把跨来源的数字痕迹，稳定变成用户认可的“我的一天”和“关于我的长期记忆”，同时让用户知道每条结论从哪里来，并能随时纠正或撤回。

因此，Ameme 的初步差异化不应是“记录得更多”，而应是：

- Evidence-backed memory：每条记忆可追溯到来源。
- Human-confirmed formation：重要记忆在进入长期层前可以轻量确认。
- Progressive capture：先用低风险元数据和一键补充，按用户选择逐步增加来源。
- Portable context：用户能导出，并可通过 MCP/API 给自己选择的 AI 使用。
- Reflection loop：日报不是终点，用户的修正会反向改善分类、重要性和个性化模型。

## 4. 建议的首批用户

### 推荐：已经使用 Coding Agent 的高信息密度知识工作者

具体画像：产品经理、研发、AI 研究者、独立开发者和小团队创始人；每天跨浏览器、文件、Git、终端和 AI 对话工作；已经感受到上下文丢失，并理解本地工具、MCP 或 Skill。

他们最强的首版任务不是“保存人生”，而是：

1. 下班时自动还原今天推进了什么。
2. 一周后准确回答某个项目何时、为何发生变化。
3. 在新的 AI 会话里提供最近项目背景，不必重复解释。
4. 把工作事实整理成可修正的日报/周报，而不是监控式工时统计。

选择这群人的原因：

- 数字痕迹集中在电脑，采集可行性最高。
- 痛点高频，价值可以在一天内被感知。
- 能容忍早期桌面 Agent 和 MCP 形态。
- 有更高付费意愿，也能提供高质量反馈。

暂不作为首批用户：希望自动记录全部生活的大众用户。原因不是终局不覆盖，而是手机权限、IM 接入、账单识别、家庭隐私和跨端同步会同时引入过多变量，难以判断产品失败究竟来自采集、理解还是价值不足。

## 5. 首版产品形态候选

### 方案 A：全自动桌面记录器

后台持续捕获屏幕、浏览器、文件、终端和会议，自动生成日报。

- 优点：最接近“无感”。
- 风险：隐私和资源占用最大；与 Recall、screenpipe 的能力高度重叠；错误信息量巨大。

### 方案 B：渐进式桌面记忆助手（推荐）

后台只采集低风险活动元数据，用户需要时按一个快捷键捕获当前上下文；每天生成一张可核对的“我的一天”，经用户确认后形成长期记忆。

- 默认采集：活跃应用、窗口标题、浏览器页面标题/域名、文件变更元数据、Git 提交。
- 显式捕获：当前页面正文、截图、选中文本、剪贴板、当前文件摘要。
- 默认不采：键盘内容、密码字段、全天音频、私聊正文、隐身窗口、用户设置的排除应用/目录。
- 输出：时间线、项目推进、关键决定、未完成事项、待用户确认的长期记忆。
- 交互：桌面托盘 + 全局快捷键 + 本地 Web/桌面时间线 + MCP 查询。

这一方案把“无感”定义为无需重新书写，而不是无需授权、无需知情。它也允许我们先验证 Memory Formation，而不是先制造海量原始数据。

### 方案 C：一键日记助手

不做后台采集，用户按键后收集当前窗口、最近文件、选择的截图/照片/账单，再由 AI 整理。

- 优点：隐私边界最清晰，开发最快。
- 风险：仍依赖用户想起来按键，无法自动还原完整的一天。

## 6. 推荐的 MVP 闭环

建议采用方案 B，并把第一版严格限制为 Windows 单机、工作上下文、单用户：

```text
可见且可暂停的本地采集
  -> 事件去重与会话分段
  -> 项目/任务/人物/决定候选
  -> 每日晚间“我的一天”草稿
  -> 用户接受、修改、删除
  -> 确认后的长期记忆
  -> 时间线搜索与 MCP 查询
```

首版只需支持三种核心对象：

- Activity：可验证的行为事实。
- Episode：一段有共同目标的活动，例如“完善支付 PRD”。
- Memory：经过确认或高置信规则形成、未来值得召回的事实/决定/偏好。

先不引入独立图数据库。SQLite + 全文检索 + 向量索引足以验证产品；关系可用普通表表达。只有在跨实体关系查询被真实使用后再评估图数据库。

## 7. 第一阶段成功标准

不以采集事件数或日报生成率作为核心成功指标。建议验证：

- Day Reconstruction Accuracy：用户认为当天重要事项被正确还原的比例。
- Correction Burden：用户完成核对所需时间，以及每条内容的修改率。
- Memory Acceptance Rate：候选长期记忆被接受的比例。
- Useful Recall Rate：历史查询中结果真正帮助用户继续工作的比例。
- Week-4 Retention：四周后仍查看或确认日报的比例。
- Privacy Trust：用户是否愿意保持采集开启，以及主动排除/删除是否顺畅。

首轮原型目标建议：5–10 名目标用户连续使用 14 天；每天核对不超过 2 分钟；重要事项还原率达到 70% 以上；不存在无法解释来源的长期记忆。

这些阈值目前是产品假设，不是已验证事实。

## 8. 关键风险

1. 捕获不等于理解：窗口标题和文件变更可能无法还原真实任务。
2. 全量截图会让隐私、存储和处理成本先于用户价值爆炸。
3. 自动推断情绪、关系和“效率”容易制造伪洞察，首版应避免无证据判断。
4. 公司设备与 IM 数据可能受组织政策限制，必须支持排除与本地模式。
5. 日报可能只是新鲜感；必须用 14–30 天行为验证长期价值。
6. MCP 是渠道，不是普通用户产品；它不能代替可见、可纠正的记忆界面。

## 9. 本阶段确认门

进入系统蓝图和 MVP PRD 前，需要确认三个决策：

1. 首批用户是否锁定“使用 Coding Agent 的高信息密度知识工作者”？
2. 第一版是否选择“Windows 渐进式桌面记忆助手”，而不是全量屏幕/音频记录器或纯一键日记？
3. 第一版核心承诺是否采用：“每天两分钟确认，自动形成可信的工作记忆，并能供 AI 调用”？

确认后，下一阶段交付：

- 用户任务与访谈提纲
- 端到端产品流程
- 数据采集权限矩阵
- Event / Episode / Memory Schema
- 本地优先技术架构与模型调用策略
- MVP PRD、开发拆分、成本模型和验证计划
